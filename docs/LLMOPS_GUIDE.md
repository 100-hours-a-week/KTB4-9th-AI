## 1. 파이프라인 개요

COSMOS LLMOps 파이프라인은 72건의 표준 평가 요청을 기준으로 후보 모델의 문제 생성 능력을 정량 평가하고, 검증 기준을 통과한 모델만 운영 환경에 안전하게 배포할 수 있도록 지원한다.

```mermaid
flowchart LR
    A["후보 모델 선정<br/>(오픈소스 베이스 / 파인튜닝)"] --> B["GitHub Actions<br/>원클릭 평가 실행"]
    B --> C["1단계: 문제 생성<br/>(서버리스 GPU)"]
    C --> D["2단계: 품질 검증<br/>(정적·모순·Judge0 실행)"]
    D --> E["성적표 자동 산출<br/>(실질 통과율 / 폐기 분석 / 비용)"]
    E --> F["관측 및 분석<br/>(GitHub 요약 / Langfuse / MLflow)"]
    F --> G["운영 승격 승인<br/>(버튼 클릭 시 SSM 반영)"]
```

## 2. 필요한 환경변수 및 GitHub Secrets 설정

모델 평가와 품질 검증 파이프라인이 정상 동작하려면 아래 환경변수들이 준비되어 있어야 한다. GitHub Actions를 통해 자동 평가를 진행할 때는 저장소의 **GitHub Secrets**에 등록되어 있어야 하며, 로컬 PC에서 테스트할 때는 루트 경로의 `.env` 파일에 기입한다.

### 2.1 GitHub Secrets 등록 위치
저장소 상단 메뉴의 **`Settings` → `Secrets and variables` → `Actions`** 경로에서 아래 항목들을 등록하거나 관리한다.

### 2.2 필수 환경변수 목록

| 환경변수 이름 | 등록 위치 | 용도 및 설명 |
|---|---|---|
| `MODAL_TOKEN_ID` | GitHub Secrets / `.env` | Modal 서버리스 GPU 인프라 구동 및 vLLM 엔드포인트 자동 배포를 위한 인증 ID |
| `MODAL_TOKEN_SECRET` | GitHub Secrets / `.env` | Modal API 접근용 비밀 키 |
| `HF_TOKEN` | GitHub Secrets / `.env` | HuggingFace 접근 토큰. 비공개 모델 가중치를 다운로드할 때 필수 사용 |
| `GEMINI_API_KEY` | GitHub Secrets / `.env` | 2단계 채점 과정에서 문제 논리 모순 검사, 테스트케이스 및 기준 코드 생성을 수행하기 위한 API 키 |
| `JUDGE0_URL` | GitHub Secrets / `.env` | 생성된 문제의 입출력 예시와 기준 코드를 직접 컴파일·실행하여 검증하는 채점 서버 주소 |

| `AWS_ACCESS_KEY_ID` | GitHub Secrets / `.env` | MLflow 평가 결과 원본 파일 저장 및 운영 배포 승격을 위한 AWS 인증 키 |

| `DISCORD_WEBHOOK_URL` | GitHub Secrets / `.env` | 평가 완료 성적표 및 운영 승인 요청 알림을 팀 채널로 전달하는 웹훅 주소 |

## 3. GitHub Actions 원클릭 모델 평가 실행

복잡한 인프라 설치나 로컬 환경 구성 없이 GitHub 웹 화면에서 파라미터 입력만으로 모델 평가를 시작할 수 있다.

### 3.1 실행 방법

1. GitHub 저장소 상단 메뉴에서 **`Actions`** 탭을 클릭한다.
2. 좌측 목록에서 **`LLMOps Evaluation & Release`** 워크플로를 선택한다.
3. 우측의 **`Run workflow`** 버튼을 누르고 필요한 항목을 설정한 뒤 실행한다.

### 3.2 입력 항목 안내

| 항목 이름 | 기본값 | 선택 및 입력 가이드 |
|---|---|---|
| `track_type` | `base_model` | • `base_model`: 오픈소스 원본 베이스 모델을 벤치마크할 때 선택<br>• `trained_model`: 직접 파인튜닝하여 HuggingFace에 올린 모델을 평가할 때 선택 |
| `model_id` | `Qwen/Qwen3.5-122B-A10B-FP8` | 평가할 HuggingFace 모델 레포지토리 이름<br>예: `Qwen/Qwen3-32B`, `your-org/cosmos-qwen3-8b-merged` |
| `prompt_version` | `generate_problem/v11` | 리포트 및 실험 기록에 표시할 프롬프트 버전 식별자 |
| `gpu_type` | `H200` | 추론을 수행할 클라우드 GPU 기종 (하단 추천 표 참고) |
| `limit` | `0` | • **`0`**: 72건 전체 정식 평가 (약 15~20분 소요)<br>• **`4`**: 파이프라인 정상 동작 여부만 빠르게 확인하는 스모크 테스트 (약 4~5분 소요) |
| `concurrency` | `12` | 동시에 처리할 문제 생성 요청 수. 서버리스 환경 기준 `12`가 가장 안정적 |

### 3.3 모델 크기별 추천 GPU 기종

| GPU 기종 | 메모리 | 시간당 비용 | 권장 모델 체급 |
|---|---|---|---|
| **`H200`** (기본 권장) | 141GB | `$4.54 / hr` | `122B-FP8`, `70B~72B` 대형 모델 고속 추론 |
| **`B200`** | 180GB | `$6.25 / hr` | 초대형 모델 추론 |
| **`2xA100`** | 160GB (80GB×2) | `$5.00 / hr` | 분산 병렬 처리가 필요한 대형 모델 |
| **`A100`** | 80GB | `$2.50 / hr` | `14B ~ 32B` 모델 |
| **`L40S`** | 48GB | `$1.95 / hr` | `7B ~ 14B` 모델 |
| **`L4`** | 24GB | `$0.80 / hr` | `4B ~ 8B` 소형 모델 또는 경량화 모델 |

## 4. 평가 결과 및 성적표 분석 방법

평가가 완료되면 GitHub Actions 실행 화면 하단의 **`Summary`** 영역에 종합 성적표가 표시된다.

### 4.1 핵심 성적표 항목

1. **실행 환경 및 비용 요약**:
   - 평가 대상 모델 및 프롬프트 버전
   - 사용한 GPU 기종 및 실제 문제 생성 시간
   - **예상 GPU 과금액**: 추론에 순수 사용된 시간 기준 비용
   - **실질 통과율**: 서비스 출제 기준을 만족한 문제의 비율
   - **Langfuse 트레이스 바로가기 링크**: 문제별 상세 분석 페이지 연결
2. **품질 검증 세부 지표**:
   - **검증 통과율**: 정적 검증, 모순 검사, Judge0 의미 검증을 통과한 비율
   - **실질 통과율**: 검증을 통과한 문제 중 **시간 제한(`100ms ~ 20초`)과 메모리 제한(`32MB ~ 2GB`)까지 정상 범위**에 들어와 실제 출제 가능한 비율 (COSMOS의 핵심 채택 기준)
   - **단계별 폐기율**: 형식 오류, 정적 검증 폐기, 논리 모순 폐기, 의미 검증 폐기(기준 코드 오답 등) 비율
3. **난이도 및 유형별 통과율**:
   - `LV1`부터 `LV5`까지 난이도별 성공률
   - `DP`, `GREEDY`, `GRAPH` 등 16개 알고리즘 유형별 문제 생성 성공률

## 5. Langfuse 대시보드 상세 분석 가이드

모든 평가 과정은 관측 플랫폼인 Langfuse에 실시간 기록된다. 72건 전체 요약부터 개별 문제의 단계별 입출력과 탈락 원인까지 세밀하게 추적할 수 있다.

### 5.1 Langfuse 계층 구조 이해

Langfuse의 데이터는 다음과 같은 3단계 계층 구조로 체계화되어 있다.

1. **세션 (`Session`)**:
   - 1회의 전체 평가 실행 단위다.
   - 식별자 형식: `eval-<GitHub Run ID>` (예: `eval-40290654411`) 또는 로컬 실행 라벨명
   - 72건의 문제 평가 요청 전체가 하나의 세션으로 묶여 총 비용과 전체 통과율이 합산된다.
2. **트레이스 (`Trace`)**:
   - 1건의 문제 생성 요청 단위다.
   - 식별자 형식: `<세션ID>:v1-0001:LV3:GREEDY` (문제 번호, 난이도, 알고리즘 유형 포함)
   - 각 문제마다 1단계 생성과 2단계 채점이 하나의 트레이스 안에 통합되어 기록된다.
3. **관측 스팬 (`Observations`)**:
   - 트레이스 내부에서 실행되는 세부 노드별 실행 기록이다.
   - `generate` 분기: 후보 모델의 문제 생성 노드 (`generate_problem`)
   - `score` 분기: 정적 검증(`static_validate`) → 논리 모순 검사(`check_contradiction`) → 테스트케이스 생성(`generate_testcase`) → 기준 코드 생성(`generate_ref_code`) → Judge0 실행(`semantic_validate`)

### 5.3 세션 목록 및 최종 평가 리포트 확인법

1. 좌측 메뉴에서 **`Sessions`**를 클릭한다.
2. 목록에서 확인하고자 하는 평가의 세션 ID(`eval-<run_id>`)를 클릭한다.
3. 세션 상세 페이지에서 다음 정보를 즉시 확인할 수 있다:
   - **`Total Cost`**: 해당 평가 전체에서 발생한 총비용 (서버리스 GPU 생성 비용 + 채점에 사용된 API 비용 합산)
   - **`Trace Count`**: 생성된 총 문제 수 (스모크 테스트 4건 또는 정식 평가 72건 + 최종 요약 리포트 1건)
   - **최종 평가 리포트 확인 (`<세션ID>:SUMMARY`)**:
     - 트레이스 목록 맨 위의 **`<세션ID>:SUMMARY`** 트레이스를 클릭한다.
     - **`Output`** 탭을 열면 GitHub Actions 요약 화면과 동일한 **마크다운 최종 성적표 전문(확정 건수, 실질 통과율, 단계별 폐기 분석, 난이도별/알고리즘 유형별 통과율 표)**이 Langfuse 웹상에 그대로 렌더링되어 표시된다.
     - **`Input`** 탭에서는 평가 당시의 모델명, GPU 기종, 시간당 단가, 실제 과금 시간, GitHub Actions 실행 페이지 링크를 확인할 수 있다.
     - **`Scores`** 탭에서는 실질 합격 여부(`usable`), 총 GPU 비용(`gpu_cost_usd`), 평가 완료 상태(`outcome: COMPLETED`) 배지를 확인한다.

### 5.4 트레이스 목록 탐색 및 필터링 활용법

좌측 메뉴의 **`Traces`** 화면에서는 생성된 개별 문제들을 다각도로 필터링하여 분석할 수 있다.

#### ① 기본 화면 구성
- **`Name`**: 문제 식별자 (예: `eval-40290654411:v1-0012:LV2:DP`)
- **`User`**: 실행 트랙 유형 (`base_model` 또는 `trained_model`)
- **`Latency`**: 해당 문제 1건의 생성 및 채점 전체에 소요된 총 시간
- **`Cost`**: 해당 문제 1건에서 발생한 비용
- **`Scores`**: 채점 결과 배지 (`passed: 1`, `usable: 1` 등)

#### ② 필수 추천 필터
화면 상단 **`Filter`** 버튼을 눌러 다음 조건을 설정하면 분석 시간을 크게 단축할 수 있다:
- **방금 실행한 평가만 모아보기**: `Session ID` = `eval-4029...` 입력
- **탈락한 문제만 골라내기**: `Score` → `passed` = `0` (또는 `usable` = `0`)
- **특정 탈락 사유만 모아보기**: `Score` → `outcome` contains `REF_CODE_FAILED` 또는 `PROBLEM_CONTRADICTION`
- **최상위 문제 단위로만 보기**: 상단 필터에서 `Root observation only`를 활성화하여 하위 스팬들이 목록에 섞여 나오는 것을 방지

### 5.5 문제 1건 심층 디버깅 방법 (트레이스 상세 분석)

트레이스 목록에서 특정 문제를 클릭하면 우측에 상세 분석 패널이 열린다.

#### ① 그래프 뷰 전환
- 우측 패널 상단에서 목록 형태의 뷰 대신 **`Graph`** 아이콘을 클릭한다.
- 좌측 `generate` 분기와 우측 `score` 분기로 이어지는 시각적 파이프라인 그래프가 표시된다.

#### ② 노드별 입출력 원문 검사
그래프에서 특정 노드 상자를 클릭하면 해당 노드의 세부 정보가 서브 패널에 표시된다:
- **`generate_problem` 노드 클릭 시**:
  - `Input`: Few-shot 참고 문제 3건을 포함하여 후보 모델에 실제로 주입된 프롬프트 전문 확인
  - `Output`: 후보 모델이 출력한 원본 문제 JSON 데이터 전문 확인
  - `Model`: 실제 추론에 사용된 모델명 (예: `Qwen/Qwen3.5-122B-A10B-FP8`)
  - `Usage`: `prompt_tokens`, `completion_tokens`, `total_tokens` 사용량 확인
- **`check_contradiction` 노드 클릭 시**:
  - 채점용 검증 모델이 문제 설명과 입출력 예시 사이에 논리 모순이 있다고 판단한 근거 텍스트 확인
- **`generate_ref_code` 노드 클릭 시**:
  - 생성된 문제를 풀기 위해 채점기가 작성한 정답 기준 코드 확인
- **`semantic_validate` 노드 클릭 시**:
  - Judge0 채점 서버에서 실행된 테스트케이스별 실제 실행 결과, 표준 출력, 컴파일 오류 메시지 확인

#### ③ 점수 탭 확인 (`Scores`)
우측 패널 상단의 **`Scores`** 탭을 누르면 해당 문제에 기록된 정량 채점 지표를 확인할 수 있다:
- **`passed`**: `1` (최종 합격) 또는 `0` (폐기)
- **`usable`**: `1` (실제 출제 규격 통과) 또는 `0` (비정상 시간/메모리 제한 등으로 실무 출제 불가)
- **`outcome`**: 구체적인 탈락 단계와 코드 (예: `semantic_validate:REF_CODE_FAILED`, `check_contradiction:PROBLEM_CONTRADICTION`, `PASSED`)
- **`Comment`**: 검증기가 남긴 탈락 사유 요약 메시지
- **`gpu_cost_usd`**: 문제 생성에 소요된 GPU 단가 기준 과금액

### 5.6 프롬프트 보관함 및 버전 비교 (`Prompts`)

좌측 메뉴의 **`Prompts`** 탭에서는 COSMOS 문제 생성 파이프라인 전반에 쓰이는 10종의 시스템 프롬프트를 확인하고 관리할 수 있다.

1. 프롬프트 목록에서 `generate_problem` 등 원하는 항목을 클릭한다.
2. 상단 버전 선택창에서 현재 버전(`v11`)과 이전 버전(`v10`, `v9` 등)을 선택해 프롬프트 변경 사항을 나란히 비교할 수 있다.
3. 각 버전 아래에서 해당 프롬프트를 거쳐간 실제 호출 횟수, 평균 지연 시간, 평균 토큰 수 변화를 확인하여 프롬프트 개선 효과를 정량적으로 검증할 수 있다.

## 7. 검증된 모델 운영 반영 및 롤백 절차

우수한 성능을 보인 모델은 별도의 서버 재배포나 코드 수정 없이 승인 버튼 클릭 한 번으로 운영 서비스에 즉시 반영할 수 있다.

### 7.1 운영 배포 승격 절차

1. 모델 평가 워크플로가 끝나면 성적표와 함께 디스코드로 평가 완료 및 배포 승인 요청 알림이 전송된다.
2. GitHub Actions 실행 페이지 상단의 노란색 안내 배너에서 **`Review deployments`** 버튼을 누른다.
3. `production-approval` 항목을 선택하고 코멘트를 입력한 뒤 **`Approve and deploy`**를 클릭한다.
4. 승인이 완료되면 AWS 파라미터 저장소의 운영 모델 설정이 해당 모델로 즉시 변경된다.
5. 운영 백엔드는 매일 새벽 정기 문제 생성 시 변경된 최신 모델을 자동으로 읽어와 출제한다.

### 7.2 안전장치 및 긴급 복구

- **자동 대체 생성**: 운영 환경에서 해당 모델 추론 서버에 일시적 장애가 발생하면, 시스템이 자동으로 기본 모델로 전환하여 문제 생성을 중단 없이 완료한다.
- **신속 롤백**: 배포된 모델에 예기치 못한 이슈가 있을 경우, AWS 파라미터 저장소의 모델 설정을 이전 모델 이름으로 변경하면 즉시 이전 상태로 복구된다.

## 8. 자주 묻는 질문

### Q1. 평가 중 일시적인 네트워크 오류로 몇 건이 실패하면 처음부터 다시 평가해야 하나요?
- 그렇지 않다. 평가 시스템은 이미 성공한 문제를 건너뛰는 이어하기 기능을 지원하므로, 인프라 일시 오류로 중단된 건만 골라서 안전하게 재시도할 수 있다.

### Q2. 팀원이 비공개로 등록한 HuggingFace 모델도 평가할 수 있나요?
- 가능하다. GitHub Secrets에 등록된 `HF_TOKEN`이 해당 비공개 레포지토리의 읽기 권한을 가지고 있다면 정상적으로 다운로드하여 평가를 진행한다.
- 단, LoRA 어댑터 단독 형태가 아닌 베이스 모델과 가중치가 합쳐진 전체 가중치 모델로 등록되어 있어야 서버리스 GPU에서 바로 서빙된다.

### Q3. 검증 통과율과 실질 통과율은 어떻게 다른가요?
- **검증 통과율**: 문제의 문법, 논리적 모순, 실행 가능성 검증을 통과한 비율이다.
- **실질 통과율**: 검증 통과 문제 중 시간 제한과 메모리 제한이 실제 코딩 테스트 표준 규격 안에 들어와 **실제 사용자에게 즉시 출제 가능한 완성형 문제의 비율**이다. COSMOS에서는 이 실질 통과율을 모델 채택의 핵심 지표로 삼는다.
