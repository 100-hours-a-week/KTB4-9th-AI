# ADR-0001: 핵심 풀이(algorithm_core) 임베딩 유사도로 중복 문제를 거른다

## 상태

채택

## 상황

문제는 LLM이 생성하고, 배치는 (카테고리, 난이도) 조합마다 재고를 채우도록 매일 여러 개를 만든다.
같은 카테고리에서 반복해서 만들다 보면 이야기 설정과 입출력 형식만 다르고 푸는 방법은 같은 문제가 나온다.
사용자에게는 같은 문제를 다시 푸는 것과 같으므로 저장하기 전에 걸러야 한다.

## 선택지

### A. 지문 전체를 비교한다

- 지문이나 제목의 텍스트, 또는 지문 전체 임베딩을 비교한다.
- 이야기 설정("상점", "택배" 등)과 입출력 형식이 유사도를 크게 좌우한다.
- 같은 알고리즘이라도 이야기가 다르면 다른 문제로 판단해 중복을 놓친다.

### B. 핵심 풀이 한 문장(algorithm_core)만 임베딩해 비교한다

- 문제를 만들 때 "어떤 조건에서 무엇을 어떤 알고리즘으로 계산하는지"를 한 문장으로 함께 만든다.
- 이야기와 입출력 형식을 빼고 풀이만 비교하므로 같은 알고리즘의 문제를 잡을 수 있다.
- algorithm_core의 품질에 따라 판정이 달라진다.

## 결정

B를 택한다.

- `generate_problem`이 문제와 함께 `algorithm_core`를 만든다.
- `check_duplicate`가 `algorithm_core`를 `gemini-embedding-2`(768차원, `SEMANTIC_SIMILARITY`)로 임베딩한다.
- **같은 카테고리**의 기존 문제 임베딩과 코사인 유사도를 비교한다(pgvector).
- 가장 비슷한 문제의 유사도가 **0.87 이상**이면 `DUPLICATE`로 폐기한다.
- 통과한 문제는 `finalize`가 저장하면서 임베딩을 색인에 추가한다.
- 임베딩 호출이나 DB 조회에 실패하면 확인하지 못한 문제를 저장하지 않도록 폐기한다.

## 이유

### algorithm_core에 문제만의 조건을 넣는다 (generate_problem v6)

처음에는 "BFS로 최단 거리를 구한다"처럼 알고리즘 이름만 적혀,
알고리즘만 같고 조건이 다른 문제까지 중복으로 폐기됐다.
"벽을 최대 한 번 부술 수 있다는 조건에서 BFS로 최단 거리를 구한다"처럼
이 문제만의 조건을 포함하도록 프롬프트에 좋은 예와 나쁜 예를 넣었다.

### 기준값 0.87은 실측으로 정했다

gemini-embedding-2로 문제 122개, 폐기 57건을 측정했다.

| 비교 대상 | 유사도 |
|---|---|
| 같은 카테고리의 서로 다른 문제 (434쌍) | 중앙 0.718, p95 0.815 |
| 다른 카테고리 (6947쌍) | 중앙 0.649, p95 0.723 |
| 중복으로 걸러진 문제 (57건) | 최소 0.852, 중앙 0.896 |

- 0.70~0.85 구간에 61%가 몰려 있어 데이터만으로 경계가 뚜렷하게 나뉘지 않는다.
- 기존 기준 0.85에서 폐기된 문제 중 0.85~0.87 구간 10건을 직접 검토했더니,
  자료구조만 같고 계산 대상이 다른 오탐이었다.
- 그래서 0.85에서 0.87로 올렸다.

### 같은 카테고리 안에서만 비교한다

다른 카테고리의 문제는 유사도가 낮고(p95 0.723), 비교 대상을 줄여 조회 비용을 줄인다.

## 결과

- 이야기만 바꾼 같은 풀이의 문제가 저장되지 않는다.
- 판정이 algorithm_core 품질에 달려 있다. 프롬프트를 바꾸면 중복 폐기율을 다시 확인해야 한다.
- 기준값을 다시 정할 때는 `problem_embeddings`가 아니라 `discarded_problems`를 봐야 한다.
  색인에는 기준을 통과한 문제만 남아 최댓값이 기준선 바로 아래에서 잘리기 때문이다.
- 같은 카테고리를 동시에 생성하면 서로의 임베딩이 아직 색인에 없어 둘 다 통과할 수 있다.
  배치는 같은 카테고리가 연달아 생성되지 않도록 순서를 섞는다(`interleave`).
- 배틀 문제도 같은 방식을 쓰지만 기준값은 0.85이며, 배틀 데이터로 따로 측정하지 않았다.
